# ZeroHop — Contexto do projeto

App desktop Electron para compartilhamento de tela, chat de voz e chat de texto em grupo entre amigos, sem servidor próprio hospedado. Uso pessoal, para jogar com amigos enquanto compartilha tela/jogo. Renomeado de "ScreenShare" pra "ZeroHop" (v0.23.0+) porque o escopo cresceu além de só compartilhar tela. O repositório antigo (`electron-screen-share`) foi apagado e recriado como `murilobarbosa2002/zerohop`; o pacote npm também se chama `zerohop` agora (era `zero-hop`), o que muda a pasta de `userData` no Windows pra `%APPDATA%\zerohop\`.

Convenções de código, arquitetura, commits e Markdown estão em `.claude/CONVENTIONS.md` — leia antes de mexer em qualquer coisa.

## Decisões de arquitetura já tomadas

- **Sem servidor próprio.** Sinalização via PeerJS (broker público gratuito, `0.peerjs.com`). Vídeo/áudio sempre P2P direto (WebRTC).
- **TURN desativado de propósito.** O usuário decidiu explicitamente NÃO usar TURN (relay) — só STUN. Motivo: qualquer TURN gratuito viável tem limite de banda muito baixo (5GB/mês testado com Metered.ca) e o usuário prefere que a conexão falhe a depender de um relay limitado. Ver `src/renderer/src/services/room/turnCredentials.ts` — está fixo em STUN-only. **Não reativar TURN sem pedir confirmação explícita.**
- **Stack do renderer: React + TypeScript + Tailwind CSS, via `electron-vite`** (migração concluída — antes era JS vanilla sem bundler). `npm run dev` = dev server com hot-reload; `npm run build` = bundle de produção em `out/`; `npm run typecheck` roda o `tsc -b --noEmit`. PeerJS é dependência normal do npm agora (não é mais vendorizado).
- **Visual retrô Windows 98/ICQ (v0.31.0+), pedido explícito do usuário.** Os tokens de cor/raio em `tailwind.config.js` foram remapeados pra paleta cinza clássica (fundo `#d4d0c8`, texto preto, accent navy `#000080`); `src/renderer/src/index.css` tem duas regras globais que fazem o reskin cascatear automaticamente pra quase todo componente sem precisar editar cada um: `[class*='rounded-']:not(.rounded-full) { border-radius: 0 !important; }` (zera qualquer arredondamento, menos `rounded-full` que fica reservado pra avatares/indicadores circulares) e `.border { box-shadow: inset ... }` (aplica o bisel 3D "para fora" em cima de QUALQUER elemento com a classe `.border` do Tailwind, sem precisar tocar em `border-color`; inputs/select/textarea/video/audio recebem o bisel invertido "afundado" via seletor de tag). A fonte é `Jersey10` (SIL OFL, baixada em `src/renderer/src/assets/fonts/`, `@font-face` local — **não carregar fontes de CDN externo em runtime**, esse projeto valoriza rodar sem depender de rede externa além do broker PeerJS). Era `Pixelify Sans` até a v0.35.0, trocada na v0.35.1 porque o "c" minúsculo dela ficava quase idêntico ao "d" — **testar sempre a legibilidade de letras parecidas (c/d, m/n, etc.) antes de adotar uma fonte pixelada nova**, esse tipo de fonte sacrifica clareza de propósito, mas não deveria sacrificar a ponto de confundir letras. Ao adicionar QUALQUER componente novo, usar sempre os tokens semânticos existentes (`bg-panel`, `border-border`, `text-text`, etc.) em vez de cores/raios soltos — é assim que o reskin continua se aplicando automaticamente.
- **Arquitetura de sala:** malha P2P (mesh) via `RoomClient`. Um código de sala curto (6 caracteres) = o ID do peer de quem criou a sala. Cada novo membro troca uma `DataConnection` com quem já está na sala (protocolo de "fofoca"/gossip para propagar a lista de membros). Vídeo só é enviado a quem pede explicitamente ("watch-request"), não é broadcast automático — economiza banda de quem compartilha.
- **Gravar tecla de atalho relatado como "não funciona" (v0.36.9) — causa raiz não confirmada, mas diagnóstico agora existe.** Se `startGlobalHotkeys()` falhar silenciosamente (por padrão, tolerante a falha) num Windows real, `recordNextHotkey()` fica esperando pra sempre sem nenhum aviso, porque nada nunca dispara o `keydown` que resolveria a gravação. Corrigido na v0.36.11 com duas coisas: (1) `src/main/globalHotkeys.ts` agora grava em `LogCategory.HOTKEYS` (tela de Logs) se a captura global iniciou com sucesso ou não — antes falhava 100% em silêncio, sem deixar rastro nem pro usuário nem pra depuração futura; (2) `HotkeyRecorderRow.tsx` tem um timeout de `RECORD_HOTKEY_TIMEOUT_MS` (8s) que mostra uma mensagem clara em vez de ficar preso em "Aperte uma tecla..." pra sempre. **Se voltar a acontecer, o primeiro passo é checar a categoria "Teclas de atalho" na tela de Logs** pra saber se a captura nativa sequer iniciou.
- **Teclas de atalho globais — sem NENHUMA dependência nativa desde a v0.36.22 (histórico de idas e vindas abaixo).** Decisão explícita do usuário: depois de duas bibliotecas nativas diferentes de captura de teclado (`uiohook-napi` v0.36.9-v0.36.20, `node-global-key-listener` v0.36.21) falharem exatamente do mesmo jeito silencioso na mesma máquina real (gravar a tecla funcionava, usar de verdade não, sem nenhum log de erro nos dois casos — ver bug history mais abaixo), o usuário topou trocar confiabilidade total por uma limitação de UX: push-to-talk agora só funciona com o ZeroHop em primeiro plano.
  - **Mutar mic / mutar áudio:** usam a API nativa do Electron `globalShortcut.register(accelerator, callback)` (`src/main/toggleHotkeys.ts`) — sem dependência nativa nenhuma, é a mesma API que praticamente todo app Electron usa pra atalho global, funciona com QUALQUER outro programa/jogo em foco.
  - **Push-to-talk (v0.36.22-v0.36.24: só DOM/foco; v0.36.25+: híbrido de novo).** Base: `keydown`/`keyup` comuns do DOM no **renderer** (`renderer/src/hooks/usePushToTalk.ts`), mesmo `lib/keyboardAccelerator.ts` que mic/áudio já usavam — `pushToTalkHotkey` é `AcceleratorBinding` igual aos outros dois. Isso sozinho só dispara com a janela do ZeroHop em foco. **Na v0.36.25, o usuário decidiu reativar `uiohook-napi` (`src/main/globalHotkeys.ts`, recriado) EM PARALELO** — `usePushToTalk.ts` escuta os DOIS caminhos ao mesmo tempo (`window.api.onHotkeyPttActiveChanged`, vindo do uiohook, e o `keydown`/`keyup` do DOM), qualquer um dos dois que disparar primeiro ativa o PTT. **Não é reversão da decisão anterior, é um "melhor esforço" híbrido**: se `uiohook-napi` funcionar na máquina do usuário (não funcionou em 3 tentativas anteriores nessa mesma máquina, mesmo com antivírus ESET desativado — ver histórico abaixo), PTT passa a funcionar sem foco; se falhar (silenciosamente, como sempre falhou até agora), o fallback por DOM continua garantindo que funcione pelo menos com o app em foco. Decisão explícita do usuário depois de eu perguntar se valia a pena — ele confirmou que quer o híbrido mesmo sabendo do histórico de falhas.
  - Todas as configurações de tecla ficam em `settings.json` (main process, via `getSettings()/setHotkeySettings()`), não em `localStorage` do renderer, porque mic/áudio dependem do `globalShortcut` do main. Sempre que essas configurações mudam, o main avisa todos os renderers pelo canal `hotkeySettingsChanged` — é assim que `usePushToTalk` (que vive dentro do `<Room>`, sempre montado) sabe da tecla mais recente mesmo que o usuário tenha editado o atalho com a tela de Configurações aberta por cima.
- **Push-to-talk reaproveita o mecanismo de mute normal** (`RoomClient.setMicMuted()`, adicionado como setter explícito ao lado do `toggleMicMuted()` que já existia) em vez de um estado paralelo — ao soltar a tecla (com o atraso configurável antes de mutar de novo), chama `setMicMuted(true)`; ao segurar, `setMicMuted(false)`. Isso mantém o indicador visual de "mutado" e o som de mutar/desmutar sempre corretos, sem precisar de um flag extra de "PTT ativo" competindo com o mute manual.
- **Mixer de efeitos sonoros por categoria (v0.36.9+).** Substituiu o slider único de volume por 5 categorias (`SoundCategory` em `constants/soundEffects.ts`: Interface, Sala, Chat, Chamada de voz, Compartilhamento — decisão explícita do usuário sobre o agrupamento). Cada `playXSound()` em `services/soundEffects.ts` informa sua categoria pra função `play()` compartilhada, que busca o volume daquela categoria especificamente. Armazenado como um objeto JSON só (`screenshare:soundEffectsVolumesV2` no `localStorage`), com migração automática do valor único antigo (`screenshare:soundEffectsVolume`) pra todas as categorias na primeira leitura, preservando a preferência de quem já usava o app.
- **Todo som do app é único, nunca repetido (pedido explícito do usuário).** Cada ação clicável relevante — abrir uma tela, cancelar um formulário, selecionar uma opção, mudar um campo, entrar/sair de algo, iniciar/editar/parar algo — precisa do seu próprio som, gerado com timbre/frequência/envelope diferente de todos os outros já existentes. A única exceção é quando a mesma ação semântica se repete em telas diferentes (ex: "Voltar" em várias telas usa um único `playBackButtonSound()`, porque é sempre a mesma ação). Regra completa e como sons são estruturados/sintetizados está em `.claude/CONVENTIONS.md` (seção "Efeitos sonoros") — ler antes de adicionar qualquer interação nova, som novo, ou tela nova.
- **Múltiplas salas simultâneas (v0.35.0+).** `RoomClient` é uma classe autocontida sem estado global (cada `new RoomClient()` tem seu próprio `PeerConnectionManager`/identidade de peer, `VoiceChat`, `MediaSharing`, `ChatService`), então dá pra ter várias instâncias vivas ao mesmo tempo. `src/renderer/src/hooks/useRoomSessions.ts` gerencia a lista de `RoomSession` (cada uma com seu `RoomClient`) e qual está em foco; `src/renderer/src/App.tsx` só monta o `<Room>` completo (vídeo/áudio de verdade) da sessão focada — as demais continuam rodando em segundo plano (mesh, chat, notificações), só sem UI de vídeo/áudio montada. **Voz é exclusiva da sessão focada**: trocar de foco chama `roomClient.pauseVoice()`/`resumeVoice()` (em `RoomClient.ts`, reaproveitam o `stopVoiceChat`/`startVoiceChat` privados que já existiam). Por causa disso, `VoiceChat.start()` (`services/room/VoiceChat.ts`) **não pode resetar `micMuted` pra `false`** mais — precisa preservar o mudo entre pausar/retomar, senão o microfone reaparece desmutado sozinho toda vez que o usuário volta o foco pra uma sala. `RoomSwitcher` (`components/RoomSwitcher/`) é a barra lateral que lista as sessões e mostra contador de não-lidas.
- **Contatos e sala pessoal (v0.36.20+).** Pedido explícito do usuário: poder chamar um amigo específico a qualquer hora sem trocar código de sala toda vez, sem precisar de servidor. Design escolhido (dos vários discutidos): cada instalação gera um **ID pessoal permanente** (`services/personalRoomPreference.ts`, `localStorage`, 10 caracteres alfanuméricos) usado como `desiredCode` num novo parâmetro opcional de `RoomClient.createRoom(name, password, avatarId, desiredCode?)` — sua "sala pessoal" é uma sala normal, só que sempre com o mesmo código, em vez do `randomRoomCode()` de sempre. Contatos ficam em `contacts.json` (main process, `main/contacts.ts` — arquivo próprio por pedido explícito do usuário, não `localStorage`, pra ficar visível/auditável como o `logs.jsonl`), cada um `{ id, name, password }` trocados manualmente uma vez fora do app (WhatsApp, Discord, etc.). "Chamar" um contato é literalmente `RoomClient.joinRoom(name, contact.id, contact.password, avatarId)` — a mesma função de sempre, só com os campos pré-preenchidos. **"Chamar" continua sem auto-aprovação** — passa pela mesma aprovação manual de entrada de qualquer sala, decisão preservada (nunca confirmar/negar entrada de forma que revele "quase acertou").
- **Convidar contatos pra uma sala nova, pulando a aprovação (v0.36.25+).** O usuário pediu explicitamente essa exceção — diferente de "Chamar" (é a OUTRA pessoa entrando na MINHA sala já criada, não eu entrando na dela). Duas peças: (1) entrega do convite via `PeerConnectionManager.sendInvite()`, uma conexão avulsa que NÃO passa pelo `registerDataConnection`/hello automático (interceptada no handler de `'data'` antes de virar `RoomMessage` normal, desviada pro dep `onInviteMessage`); (2) pular a aprovação via `RoomAuthController.preAuthorizeToken()`/`preAuthorizedTokens` — **importante: é baseado em TOKEN de uso único, não em peer ID pré-autorizado.** Tentei peer ID primeiro e não funciona: `joinRoom` sempre abre a conexão com um ID aleatório novo (`this.connections.open(undefined, ...)`), nunca com o ID pessoal do contato — então pré-autorizar `contact.id` nunca bate com quem realmente chega. O token viaja dentro do `hello` (`helloMessageSchema.inviteToken`, opcional) e é conferido em `handleJoinRequest`. **Verificação mútua obrigatória antes de sequer mostrar o convite**: quem recebe só aceita se o `hostId` (ID pessoal ESTÁVEL de quem convidou, incluído na mensagem — não é o peer ID efêmero da conexão) estiver na PRÓPRIA lista de contatos de quem recebeu — evita popup de estranho. **Limitação aceita pelo usuário**: só funciona se o contato convidado estiver com a sala pessoal dele aberta no momento (mesma limitação de "Chamar", direção invertida — sem servidor de presença não tem como alcançar alguém que não está com nenhuma sala aberta).
- **Instalador real via GitHub Actions, nunca via Wine.** O usuário recusou explicitamente instalar Wine no WSL (mesmo sabendo que só afetaria a máquina de build, não a dele). A solução foi mover a compilação do instalador NSIS pra um runner Windows real e gratuito do GitHub Actions (`.github/workflows/release.yml`, dispara em push de tag `v*`). **Nunca sugerir instalar Wine de novo** — está descartado.
- **Auto-update ativo** via `electron-updater` (`src/main/updater.js`), publicando em GitHub Releases (`publish.provider: github` no `package.json`, repo `murilobarbosa2002/zerohop`). Só funciona em build empacotado (`app.isPackaged`), não em `npm start`.
- **`npm run dist:local` (WSL) continua existindo só pra testes rápidos**, gerando a pasta portátil (`target: dir`, sem Wine) — não é mais o caminho de release oficial. O release de verdade é sempre via tag + GitHub Actions, que roda `npm run build` (Vite) antes do `electron-builder`.

## Histórico de bugs importantes (não repetir)

- **NUNCA colocar uma chave com valor `undefined` explícito num objeto que vai ser mandado por `DataConnection` do PeerJS (`sendTo`).** Ao adicionar o campo opcional `inviteToken` no `HelloMessage` (v0.36.25, feature de convidar contatos), o código escrevia `inviteToken: this.deps.getInviteToken?.() ?? undefined` sempre — ou seja, toda mensagem `hello` normal (sem convite nenhum envolvido) passou a incluir `inviteToken: undefined` explicitamente no objeto. Resultado: **TODO o fluxo normal de entrar numa sala quebrou** (guest nunca via o código da sala, host nunca via o guest na lista) — não só o de convite. Causa raiz: a serialização padrão do PeerJS não é JSON, é binária (tipo msgpack, ver `node_modules/peerjs/dist/peerjs.js`), e esse formato não lida com `undefined` do mesmo jeito que `JSON.stringify` (que simplesmente omite a chave) — o valor chega deformado do outro lado e `roomMessageSchema.safeParse` (que só aceita a chave ausente ou realmente ausente pra campos `.optional()`) rejeita a mensagem inteira, silenciosamente (só um `console.warn`, sem crash, o que tornou o diagnóstico mais difícil). Corrigido espalhando o campo condicionalmente (`...(inviteToken ? { inviteToken } : {})`) em vez de sempre incluir a chave. **Qualquer campo opcional novo em qualquer mensagem do protocolo de sala precisa seguir esse padrão — nunca `campo: valorQuePodeSerUndefined`, sempre spread condicional.** Pego a tempo porque a suíte `e2e/` inteira quebrou (`room-lifecycle`, `mesh-three-peers`, `sharing`, etc.) mesmo testes que não tinham nada a ver com convites — sinal de alerta de que o bug estava em código compartilhado por TODO join, não só no caminho novo.
- **NUNCA calcular o `transform`/centralização de um ícone SVG feito de curvas (arco, bezier) "de cabeça" — sempre medir o `getBBox()` real no navegador.** O ícone de gato do avatar (`AvatarGlyph.tsx`, `AvatarId.CAT`) foi "corrigido" na v0.36.6 com base num cálculo manual da extensão do arco do rosto (`A6 6 0 1 1 8.5 10.5`), que estimou o centro errado — o arco na verdade desenha bem mais do círculo do que o hemisfério inferior simples que eu tinha assumido. O resultado: o ícone ficou pior depois do "fix" (~2.4px fora do centro, na direção oposta). Corrigido de verdade na v0.36.15 medindo o `getBBox()` do path de verdade num `BrowserWindow` (via `webContents.executeJavaScript`) antes de calcular o `translate` necessário — só assim o valor bateu (`translate(0 -0.69)`, não o `translate(0 1.75)` de antes). **Sempre que um ícone parecer descentralizado, medir o bbox real primeiro, nunca estimar a mão as coordenadas de um arco SVG.**
- **Em `MembershipGossip.handleMembersMessage` (`src/renderer/src/services/room/MembershipGossip.ts`), nunca fazer `registry.upsert(id, ...)` ANTES de decidir se deve chamar `connectToPeer(id)`.** `PeerConnectionManager.connectToPeer` usa `isKnownMember(id) => registry.has(id)` como guarda contra reconectar em alguém que já está conectado. Como `MembershipGossip` fazia o upsert (só pra salvar o nome) antes de checar `isNew` e chamar `connectToPeer`, o guard sempre via `registry.has(id) === true` (por causa do upsert que acabou de rodar) e cancelava a tentativa de conexão. Resultado: numa sala com 3+ pessoas, dois convidados nunca conseguiam se conectar diretamente um com o outro (mesh quebrado), só cada um com quem criou a sala — de forma 100% reproduzível, sem ter nada a ver com NAT/STUN/TURN (isso foi a hipótese errada investigada antes de achar o bug de verdade). Corrigido na v0.30.2 só invertendo a ordem: decidir/chamar `connectToPeer` primeiro, upsert depois. Teste de regressão em `e2e/mesh-three-peers.spec.mjs` (3 processos Electron, confirma que os dois convidados se veem sem depender de quem criou a sala).
- **`VoiceChat.callMember` (`src/renderer/src/services/room/VoiceChat.ts`) não tinha NENHUM retry/timeout, diferente das `DataConnection`s da malha (que já usam `watchConnection`/`watchForRealDisconnect`).** Sintoma relatado: numa sala com 3+ pessoas, um participante conseguia ouvir todo mundo mas um dos outros não conseguia ouvi-lo (a `MediaConnection` de voz daquele par específico nunca conectava, e como não existia nenhum monitoramento, ficava quebrada pra sempre sem nenhuma tentativa nova). Corrigido na v0.35.2 adicionando `watchCallConnection` (monitora `call.peerConnection.iceConnectionState`, com timeout de `VOICE_CALL_CONNECT_TIMEOUT_MS` e até `VOICE_CALL_MAX_RETRIES` tentativas novas) — mesma filosofia de resiliência que a malha de dados já tinha, só que faltava pro lado de voz.
- **Mutar o microfone (`VoiceChat.setMicMuted`) só desativava `track.enabled = false` na trilha de áudio, e um usuário relatou que às vezes o áudio dele continuava saindo mesmo depois de mutado.** `track.enabled` deveria bastar pela spec do WebRTC, mas o microfone deste app passa por um grafo do Web Audio API (`services/MicCapture.ts`: `source -> gainNode -> destination`, pra aplicar sensibilidade/ganho) antes de virar a `MediaStreamTrack` enviada — não é uma trilha "crua" de um dispositivo. Corrigido na v0.36.1 mutando na ORIGEM também: `MicCaptureHandle.setMuted()` zera o `gainNode.gain.value` (guardando o ganho atual pra restaurar ao desmutar), chamado em paralelo ao `track.enabled` em todo lugar que muda/recupera o estado de mute (`RoomClient.toggleMicMuted`, `startVoiceChat`, `recaptureMicrophone`). **Não confiar só em `track.enabled` pra silenciar áudio que passou por qualquer processamento do Web Audio API** — zerar o gain na origem é mais confiável.

- **`text-on-accent` (cor do texto em botões azuis) oscilou demais entre versões — parar de mexer nisso sem confirmação explícita.** Histórico: `#ffffff` puro (até v0.36.0) → achado "forte demais, arde os olhos" → `#eef0f5` (v0.36.1) → ainda "forte" → `#c9d2e6` (v0.36.4, ficou bom por várias versões) → um relato de "parece preto" levou a reverter pra `#ffffff` + `text-shadow` (v0.36.11) → o mesmo usuário confirmou depois que a v0.36.4 (`#c9d2e6`, sem sombra) era a melhor versão e pediu pra voltar (v0.36.13). **Valor certo, confirmado pelo usuário: `#c9d2e6`, sem `text-shadow`.** O relato de "parece preto" provavelmente era build desatualizada (auto-update com "Depois" clicado) ou percepção de tela, não um bug de CSS — a cor no código sempre esteve correta quando checada. Antes de mudar essa cor de novo, pedir confirmação explícita e considerar que o usuário pode estar vendo uma versão antiga.
- **Confirmado por teste real do usuário (v0.36.13): mutar mic e mutar áudio via atalho (`globalShortcut`) gravam e funcionam normalmente. Push-to-talk (`uiohook-napi`) continua não gravando nenhuma tecla** no Windows real dele — confirma que o problema é mesmo a lib `uiohook-napi` não iniciando a captura naquela máquina especificamente (não um bug de código, já que `globalShortcut` funciona no mesmo PC).
- **Resolvido (confirmado pelo usuário na v0.36.17): a captura global de teclado (`uiohook-napi`) iniciou normalmente** — o log mostrou `Iniciando captura global de teclado...` seguido de `Captura global de teclado ativa — push-to-talk disponível`, os dois na mesma abertura do app. Não ficou claro se foi o timeout/retry da v0.36.17 que resolveu de verdade, ou se era simplesmente uma condição transitória (ex: alguma trava de uma versão anterior instalada, ou antivírus que parou de bloquear depois da reinstalação) — mas o sintoma sumiu. Push-to-talk deve estar utilizável agora; se o usuário configurar uma tecla e ainda assim não funcionar durante o uso real (diferente de só gravar a tecla), isso seria um bug novo e diferente (a captura iniciou, mas o evento de tecla em tempo real não está sendo tratado), não o mesmo problema de antes.
- **Terceira falha de campo, sintoma novo (v0.36.19→v0.36.20): o log mostrou captura ativa com sucesso na abertura do app, mas gravar uma tecla de PTT ainda assim não detectava nada** (timeout depois de 8s). Diferente das duas falhas anteriores (nunca iniciava vs. ficava 100% em silêncio) — dessa vez a inicialização funcionou, só a entrega de eventos durante a gravação que não chegou. Três sintomas diferentes da mesma dependência no mesmo computador em sessões diferentes é sinal forte de que `uiohook-napi` é simplesmente não confiável nessa máquina, não um bug de código (a mecânica de `recordNextHotkey`/`handleKeyDown` sempre esteve correta, revisada de novo nesse momento). **Decisão do usuário: trocar de biblioteca nativa mesmo assim, ciente do risco.** Trocado pra `node-global-key-listener` na v0.36.21 — ver arquitetura completa em `docs-site/tecnico/mapa-do-codigo.md` (seção "Teclas de atalho e push-to-talk"). Resumo: essa lib sobe um processo `bin/WinKeyServer.exe` separado (não assinado) em vez de rodar in-process como o `uiohook-napi` fazia — troca um tipo de risco por outro (processo externo pode ser flagado por antivírus tanto quanto um addon nativo), **não é uma correção garantida**, foi uma aposta explícita do usuário depois de eu apresentar esse trade-off. O ganho real é que agora existe `onError`/`onInfo` de verdade vindos do sistema (`IWindowsConfig`), então se falhar de novo, a categoria "Teclas de atalho" nos Logs deve finalmente mostrar informação real do sistema operacional, não só "nada aconteceu". `HotkeyBinding.keycode: number` (uiohook) virou `HotkeyBinding.key: string` (nome de tecla legível da nova lib, tipo `"SPACE"`/`"F13"`) — settings antigas com o campo `keycode` não validam mais e a tecla salva reseta, esperado numa troca de lib.
- **Quarta falha de campo, mesmo padrão, biblioteca diferente (v0.36.21→v0.36.22): `node-global-key-listener` falhou exatamente do mesmo jeito que `uiohook-napi`.** O usuário definiu F3, a gravação capturou a tecla com sucesso (confirma que a captura estava ativa e recebendo pelo menos um evento), mas segurar F3 depois não ativava nada — sem indicador, sem nenhum log novo, nem mesmo o `onError`/`onInfo` que essa lib deveria dar (o código lê o evento `close` do processo `WinKeyServer.exe` via `config.windows.onError`, que deveria logar se o processo morresse — mas nada apareceu, nem esse aviso). Investigado o código-fonte da lib (`node_modules/node-global-key-listener/build/ts/WinKeyServer.js`) pra confirmar que o wiring do `onError` estava correto — estava. Conclusão: é a SEGUNDA biblioteca nativa diferente a falhar do mesmo jeito na mesma máquina, o que descarta "biblioteca ruim" como causa e aponta pra algo específico da máquina/antivírus que bloqueia captura de teclado em nível de sistema de forma consistente, não importa a implementação. **Decisão do usuário: abandonar captura nativa de teclado de vez.** Push-to-talk virou `keydown`/`keyup` do DOM no renderer (`usePushToTalk.ts`), só funciona com o app em foco — ver arquitetura na seção "Teclas de atalho globais" mais acima e em `docs-site/tecnico/mapa-do-codigo.md`. `main/globalHotkeys.ts` foi deletado. **Não tentar uma terceira biblioteca nativa de captura de teclado sem motivo muito forte** — o padrão de evidência (2 libs, 2 falhas idênticas) é forte o bastante pra não valer a pena.
- **Achado mais preciso (v0.36.17): a categoria "Teclas de atalho" na tela de Logs fica 100% VAZIA nesse computador** — nem a mensagem de sucesso, nem a de falha aparecem, nunca. Isso descarta a hipótese original de "a lib carrega mas falha ao iniciar" (que teria logado a falha) — o mais provável é que `await import('uiohook-napi')` ou `mod.uIOhook.start()` trava (nunca resolve/retorna) especificamente nesse Windows, e como `startGlobalHotkeys()` não é aguardado em `main/index.ts` (roda em paralelo com `applyToggleHotkeys`, que é só isso que já confirmou funcionar), esse travamento nunca aparece como erro visível em lugar nenhum — só a ausência silenciosa de push-to-talk. Corrigido na v0.36.17 registrando um log **assim que a captura começa a tentar iniciar** (`captureStartingMessage`, antes de qualquer `await`) e envolvendo o carregamento e o `.start()` num `Promise.race` contra um timeout de `HOTKEYS_INIT_TIMEOUT_MS` (5s) — se a Promise de carregamento travar, o timeout resolve primeiro e um log específico de timeout aparece em vez de nada. **Limitação conhecida:** se o travamento for síncrono de verdade dentro do código nativo (bloqueia a thread principal do JS), nenhum `Promise.race` consegue socorrer isso — mas como o resto do app continua responsivo pro usuário (não é o processo inteiro travando), isso indica que não é esse o caso, e a race deve ser suficiente. Se mesmo assim só a mensagem "Iniciando captura..." aparecer e nada depois dela (nem sucesso, nem timeout), aí sim seria evidência de um hang síncrono de verdade, exigindo abandonar `uiohook-napi` como dependência nessa combinação de hardware/SO.
- **NUNCA forçar `aspect-video` (ou qualquer proporção fixa) no `<video>` que exibe o stream de alguém.** Fixar a proporção do elemento em 16:9 faz o navegador desenhar a proporção FORÇADA como caixa e encaixar o vídeo real dentro dela com `object-fit`, sobrando barra preta nos dois lados (ou em cima/embaixo) sempre que o conteúdo capturado não for exatamente 16:9 — o que é comum (jogos em janela, telas ultrawide, capturas de tela inteira em resoluções variadas). Reincidiu duas vezes: primeiro com `h-video-default` fixo (corrigido pra `aspect-video` na v0.35.x), depois o próprio `aspect-video` reapareceu como o mesmo problema, só que com proporção fixa em vez de altura fixa — o usuário pediu explicitamente "o card deve acompanhar o tamanho da stream, só o tamanho da stream deve aumentar ou diminuir". Corrigido na v0.36.12 em `ParticipantVideoPlayer.tsx`/`ParticipantVideoLightbox.tsx`/`SelfPreviewLightbox.tsx`: `<video>` sem nenhuma proporção forçada, só `width/height: auto` com um `max-width`/`max-height` como teto — assim o navegador usa a proporção intrínseca de verdade do stream (`videoWidth`/`videoHeight`), nunca uma caixa arbitrária. **Não reintroduzir `aspect-video`/`aspect-ratio` em nenhum elemento de vídeo que mostra stream de terceiros.**
- **`activeCapture.stop()`/`.start()` em `src/main/audioLoopback.ts` (dependência nativa `loopback-capture`) podem lançar exceção síncrona não tratada e derrubar o app inteiro com a tela de erro do Electron.** Relatado como `Error: Failed to stop loopback capture (HRESULT 0x8007139F)` ao ligar o áudio isolado por app junto do compartilhamento de tela — o driver WASAPI recusa "parar de novo" uma captura que já tinha parado sozinha (ex: o app de origem fechou/mudou de estado), e como `startAudioLoopback` sempre chama `stopAudioLoopback()` no início, isso disparava toda vez. Corrigido na v0.36.3 envolvendo `.start()`/`.stop()` em `try/catch` (mesma filosofia "tolerante a falha" que já vale pro `import()` dinâmico dessa lib, ver bullet abaixo — qualquer chamada síncrona a essa dependência nativa deve ser protegida, não só o carregamento).
- **NUNCA importar uma dependência nativa (native addon `.node`) de forma estática no topo de um arquivo do processo principal.** Ao adicionar `loopback-capture` (áudio isolado por app), um `import` estático no topo de `src/main/audioLoopback.ts` derrubava o app inteiro na inicialização com `Error: libpipewire-0.3.so.0: cannot open shared object file` sempre que a lib do sistema faltasse (aconteceu neste próprio ambiente de dev, que é Linux) — mesmo a feature sendo opt-in e desligada por padrão, o `require`/`import` estático já rodava e derrubava tudo antes de qualquer verificação de configuração. A correção foi trocar pra `import()` dinâmico **dentro** das funções que realmente usam a lib, com `try/catch` retornando `null` em caso de falha. Qualquer dependência nativa nova (áudio, captura, etc.) tem que seguir esse padrão de carregamento tardio e tolerante a falha, nunca import estático.
- Dependências nativas (`loopback-capture`, `node-window-manager`) precisam entrar em `build.asarUnpack` no `package.json`, senão o `.node` compilado fica preso dentro do `app.asar` e não carrega no app empacotado.
- **A flag `AllowWgcScreenCapturer`/`AllowWgcWindowCapturer`** (Windows.Graphics.Capture) já travou o PC inteiro de um usuário em Windows 10 numa tentativa antiga de forçá-la sem interruptor. Por isso ficou opt-in (desligada por padrão, com aviso de risco) por várias versões. **Na v0.30.x+, depois de re-testada e confirmada estável pelo usuário, voltou a ser ativada por padrão pra todo mundo** (`DEFAULT_EXPERIMENTAL_WGC_CAPTURE_ENABLED = true` em `src/main/constants/settings.ts`) e o toggle foi removido da tela de Configurações — decisão explícita do usuário, não uma reversão silenciosa da cautela anterior. Se voltar a causar travamento relatado por qualquer usuário, reverter o default pra `false` e trazer o toggle de volta, não insistir no forçado.
- **Compartilhar uma janela específica (não a tela inteira) pode ficar preta quando o usuário troca de janela (Alt+Tab) e a janela compartilhada sai de primeiro plano.** É o mesmo tipo de limitação do driver/compositor do Windows citada acima — alguns programas param de renderizar o próprio buffer quando não estão em foco/estão ocluídos, e a captura por `chromeMediaSourceId` de uma janela específica reflete isso. **Não tentar consertar trocando a API de captura de janela** (mesmo risco do item acima). A mitigação que existe é de produto, não de código: um aviso na tela de escolha (`ShareSourceKindChoice`) já orienta o usuário a preferir "Tela inteira" se for alternar entre janelas durante o compartilhamento — captura de tela inteira não depende do estado de foco de nenhum app específico.
- **Jogos em tela cheia exclusiva (fullscreen "de verdade", não borderless) não aparecem na lista de "Uma janela específica"** — ex: Project Zomboid relatado pelo usuário. Em fullscreen exclusivo o jogo deixa de ser uma janela normal do Windows (assume a tela direto), então a mesma API que lista janelas pro app (`desktopCapturer`) não o enxerga — é limitação do Windows, não bug do app, e **não dá pra "consertar" trocando a API de enumeração de janelas**. A orientação pro usuário é sempre a mesma dupla desta seção: trocar o jogo pra modo **Borderless/Windowed Fullscreen** nas configurações de vídeo dele (também resolve o problema de ficar preto no Alt+Tab, item acima), ou usar **"Tela inteira"** em vez de escolher a janela do jogo.
- **"Otimizações de tela cheia" do Windows causa cursor sumindo e captura travada/flickando em alguns jogos** — relatado com Project Zomboid (Java/LWJGL): com o jogo em janela e a stream ligada, o cursor do mouse some especificamente quando o jogo está em foco (reaparece se trocar de foco pra outro monitor/app e volta, mas some de novo ao focar o jogo); compartilhando "Tela inteira" em vez da janela, a imagem trava e só atualiza um frame ao dar Alt+Tab, congelando de novo quase na hora. Mesma família de causa dos dois itens acima (jogo não desenha do jeito que o compositor/API de captura do Windows espera) — **não é bug do app, não tentar consertar via flag de captura**. Mitigação que funciona: no atalho/executável do jogo, Propriedades → Compatibilidade → **"Desativar otimizações de tela cheia"**, combinado com manter o jogo em Borderless/Windowed (não fullscreen exclusivo).
- **Compartilhar "Tela inteira" pode ficar preto pra sempre (não recupera sozinho) depois de usar a ferramenta de Recorte do Windows (Win+Shift+S).** Relatado com a captura padrão (sem a flag experimental de WGC ativada). O overlay de escurecer a tela que o Recorte usa parece invalidar a sessão de captura de tela do Chromium sem que o navegador perceba: a `MediaStreamTrack` continua com `readyState: 'live'` (o evento `ended` já tratado em `MediaSharing.ts` não dispara), só que entregando frames pretos indefinidamente. **Não dá pra detectar isso de forma confiável em JS** (não existe evento de "a captura morreu de verdade" nesse cenário) e **não tentar consertar trocando a API de captura** (mesmo risco dos itens acima). A única mitigação é de produto: parar e começar a compartilhar de novo força uma sessão de captura nova e resolve.
- **Captura de áudio de uma janela específica (`chromeMediaSourceId` de tipo `window:`) sempre pega o áudio do sistema inteiro, nunca só daquele app** — limitação de longa data do Chromium/Electron, não um bug introduzido aqui. O seletor "áudio de só um app específico" existia desde antes mas nunca funcionou de verdade por causa disso. A partir da v0.28.0 existe uma correção em `src/main/audioLoopback.ts` usando `loopback-capture` (WASAPI Process Loopback) + `node-window-manager` (resolve o PID a partir do título da janela, já que o Electron não expõe PID no `desktopCapturer`). Começou como opt-in; **na v0.30.x+, depois de re-testada e confirmada estável pelo usuário, voltou a ser ativada por padrão pra todo mundo** (`DEFAULT_EXPERIMENTAL_PER_APP_AUDIO_ENABLED = true`) e o toggle saiu da tela de Configurações — mas a leitura do valor continua vindo do `settings.json` (`getSettings().experimentalPerAppAudioEnabled` via IPC), então editar esse arquivo manualmente ainda desliga a feature se algum usuário tiver problema, mesmo sem UI pra isso. Ver o bullet acima sobre import dinâmico — essa é a feature que motivou a regra. **Bug corrigido na v0.36.12:** `ShareControls.handleStart` só ativava esse caminho de áudio isolado (WASAPI loopback) quando o VÍDEO compartilhado era uma janela (`isWindowSource` checava `getCaptureSourceKind(sourcePicker.selectedId)`) — ou seja, escolher "áudio de só um app" enquanto compartilhava a **tela inteira** silenciosamente caía no caminho normal do Chromium (`chromeMediaSource:'desktop'` com o `chromeMediaSourceId` de uma janela), que — pela mesma limitação documentada acima — captura o áudio do sistema inteiro, não só daquele app. Corrigido checando o tipo do **áudio selecionado** (`getCaptureSourceKind(audioSourceId)`), não o tipo do vídeo — agora o áudio isolado por app funciona igual, seja compartilhando uma janela específica ou a tela inteira.
- **mDNS do Chromium desativado** (`disable-features: WebRtcHideLocalIpsWithMdns`) — sem isso, ICE pode falhar até em testes na mesma máquina se a resolução mDNS não funcionar no Windows do usuário. Esse flag é seguro, manter.
- **Firewalls de terceiros (ESET, etc.) podem gerenciar o Windows Firewall por baixo dos panos** — adicionar exceção pela tela nativa do Windows não resolve nesse caso; a exceção precisa ser criada dentro do próprio antivírus/firewall terceiro.
- **Sempre verificar se o build terminou de verdade antes de instruir o usuário a copiar a pasta** — já aconteceu de uma sessão reiniciar no meio do `electron-builder` e deixar `dist/` pela metade (só com `builder-debug.yml`, sem o `.exe`). Checar `ls dist/win-unpacked/ZeroHop.exe` sempre depois de buildar.
- Bump a marcação de versão em `src/renderer/src/main.tsx` (`console.log('[build] ZeroHop vX')`) a cada build entregue para teste — facilita confirmar que o usuário está testando a versão certa (visível na barra de título e no cabeçalho da tela de Logs, sem precisar de DevTools).
- **DevTools foi removido de propósito** (atalho F12/Ctrl+Shift+I desligado em `main/window.ts`) — desde que existe a tela de Logs (`components/LogsScreen/`, alimentada por `main/logger.ts` gravando em `logs.jsonl`), não faz sentido manter duas portas de auditoria abertas ao mesmo tempo. **Não reativar o atalho de DevTools** sem pedir confirmação explícita ao usuário.

- **NUNCA chamar `setState` (ou qualquer função que chame `setState`, como `focus()`/`leave()` em `useRoomSessions`) de dentro do updater funcional de outro `setState`.** Um updater funcional (`setX(current => ...)`) precisa ser puro — sob `<StrictMode>` (usado em `main.tsx`), o React invoca esses updaters duas vezes de propósito pra pegar exatamente esse tipo de impureza. Ao mover o bootstrap do `pendingSession` de `App.tsx` pra dentro de `useRoomSessions.ts` (refactor de responsabilidades), `markEntered`/`cancelPendingSession` foram escritos inicialmente como `setPendingSession(current => { setSessions(...); focus(...); return null })` — isso travou a suíte de e2e inteira (criar sala nunca terminava, `room-lifecycle.spec.mjs` ficava pendurado indefinidamente). Corrigido lendo o valor atual de um `pendingSessionRef` (mesmo padrão já usado pra `sessionsRef`/`focusedSessionIdRef`), chamando os efeitos colaterais como statements simples, e só então chamando `setPendingSession(null)` com um valor plano — exatamente o mesmo padrão que já tinha sido estabelecido (e documentado) pra `focus()`/`leave()` quando `useRoomSessions.ts` foi criado na v0.35.0. **Esse padrão (ref espelhando o state + side effects fora do updater) é obrigatório em qualquer novo método deste hook.**

- **Duas instâncias do mesmo hook React sem canal de sincronização = estado dessincronizado entre elas.** `useNotifications()` era chamado duas vezes (uma em `App.tsx`, só pro contador do sino; outra dentro de `NotificationsScreen.tsx`) — cada chamada cria seu próprio `useState`. O único evento vindo do main (`notification-added`) só disparava ao CRIAR uma notificação; marcar como lida/excluir/limpar só atualizava a cópia local otimista da tela, nunca a do `App.tsx`. Resultado relatado pelo usuário: ler a única notificação não fazia o pontinho vermelho do sino sumir. Corrigido replicando o padrão de `appendNotification` — `markNotificationRead`/`markAllNotificationsRead`/`clearNotifications`/`deleteNotification` (`src/main/notifications.ts`) agora também emitem um evento `notifications-changed` com a lista inteira atualizada, e `useNotifications.ts` escuta esse evento e sincroniza (`setEntries(fullList)`), então TODAS as instâncias do hook (sino, tela, futuras) ficam sempre consistentes. **Regra geral: qualquer estado que precise aparecer em mais de um lugar da UI ao mesmo tempo (contador + tela cheia, por exemplo) não pode depender só de mutação local otimista de cada instância de hook — precisa de um evento do main (ou um estado elevado/compartilhado) cobrindo TODAS as mutações, não só a criação.**
- **`RoomSwitcher` trocar de sala não fechava a tela sobreposta (Notificações/Logs/Configurações) que estava por cima.** `onFocus` só mudava `focusedSessionId` no hook; como qualquer overlay (`activeOverlay !== null`) é renderizado com `absolute inset-0 z-20` por cima da área da sala, a sala nova ficava escondida atrás da tela que já estava aberta. Corrigido em `App.tsx` fechando o overlay ativo (`closeOverlay()`) dentro do próprio wrapper que troca de sessão (`handleFocusSession`), que também ganhou o som de troca de sala que faltava.
- **A correção acima tinha um bug residual: clicar na aba da sala que JÁ ESTAVA focada, enquanto uma tela sobreposta (ex: Contatos) estava aberta, não fazia nada.** `handleFocusSession` tinha `if (sessionId === focusedSessionId) return;` bem no topo — mas abrir a tela de Contatos NÃO muda `focusedSessionId` (ela é um overlay por cima, a sessão focada continua sendo a mesma de antes). Resultado: o `return` cedo disparava antes mesmo de chamar `closeOverlay()`, então a tela de Contatos nunca fechava. Corrigido invertendo a ordem: sempre chamar `closeOverlay()` primeiro, só pular o `focus()`/som se já estava focado. **Regra geral: um "early return" baseado em um estado (`focusedSessionId`) que não reflete TODOS os efeitos colaterais da função (aqui, fechar overlay) vai pular efeitos que deveriam rodar sempre — separar "o que sempre deve acontecer" de "o que só deve acontecer se algo mudou".**
- **Sala automática (v0.36.26-v0.36.29) removida na v0.36.30 — decisão explícita do usuário.** Era uma segunda sala fixa (ID/senha próprios) que abria sozinha e convidava por polling (~30s) uma lista fixa de contatos marcados antecipadamente. O usuário achou que "não tem nada a ver com a pessoa" — o padrão de uso real dele era mais simples: convidar QUALQUER contato pra QUALQUER sala já aberta, na hora, manualmente. Substituída por um botão de convite dentro do `RoomToolbar` (painel inline `InviteContactsPanel.tsx`, funciona em qualquer sala aberta). **Lição:** o mecanismo genérico de convite por token (`RoomClient.inviteContact`/`hasContactJoinedViaInvite`/`preAuthorizeToken`) nunca foi exclusivo da sala automática — construí a sala automática EM CIMA dele, então a remoção foi só de UI/bootstrap/preferências, sem tocar no protocolo. Ao adicionar uma feature nova em cima de uma peça genérica já existente, isolar bem as duas facilita reverter só a feature nova depois, se for o caso.
- **`<select multiple>` nativo não dá pra restilizar direito com o tema retrô** — o destaque de seleção (fundo azul no Chromium) não respeita nenhum token de cor do app e ficou "feio" segundo o usuário, tanto em Logs quanto Notificações. Trocado por checkboxes normais (`components/CheckboxFilterGroup/`), que já reskinam automaticamente via `accent-accent` e os tokens de painel/borda de sempre. **Não usar `<select multiple>` em telas novas deste app** — preferir checkbox list desde o início.

## Ambiente de build

- Build acontece em WSL/Linux (não tem Wine instalado — usuário preferiu não instalar).
- Testes automatizados versionados em `e2e/` (rodar com `npm run test:e2e`), usando `playwright-core` (dependência normal do `package.json` agora) + `xvfb-run` contra o binário do Electron em `node_modules/electron/dist/electron`, com `ELECTRON_RUN_AS_NODE=` (vazio) no ambiente porque o WSL do usuário seta essa variável globalmente e isso faz o Electron rodar como Node puro em vez de abrir a janela.
- CI (`.github/workflows/ci.yml`) roda typecheck, build, lint:md e a suíte `e2e/` a cada push na `main` e a cada pull request.
- **`e2e/helpers/launchApp.mjs` não isolava o perfil do Electron — corrigido na v0.36.26 (motivo: virou bug real, não só cosmético).** Até a v0.36.25, todas as instâncias (mesmo spec ou execuções diferentes) compartilhavam `~/.config/Electron/` (nome padrão quando roda sem app empacotado), incluindo `contacts.json`/`settings.json`/`Local Storage` inteiro. Isso só causava falhas cosméticas (contato duplicado, `strict mode violation` por texto repetido) até a sala pessoal/automática ganharem auto-abertura no lançamento (v0.36.26): a partir daí, qualquer spec que rodasse DEPOIS de `contacts.spec.mjs` (que define uma senha de sala pessoal de verdade) herdava essa senha via perfil compartilhado, fazendo a sala pessoal auto-abrir sozinha em specs que não esperavam isso — a tela inicial ("Criar sala nova") nunca aparecia, quebrando a suíte inteira em cascata. **Corrigido dando um `--user-data-dir` único (`mkdtempSync`) por chamada de `launchApp()`** — cada instância (host, guest, qualquer processo) agora tem perfil totalmente isolado, sem exceção. Se voltar a ver "esperando 'Criar sala nova'" travando em specs que nem mexem em Contatos, suspeitar primeiro de vazamento de estado entre specs, não de lógica de sala.
