# ZeroHop — Contexto do projeto

App desktop Electron para compartilhamento de tela, chat de voz e chat de texto em grupo entre amigos, sem servidor próprio hospedado. Uso pessoal, para jogar com amigos enquanto compartilha tela/jogo. Renomeado de "ScreenShare" pra "ZeroHop" (v0.23.0+) porque o escopo cresceu além de só compartilhar tela. O repositório antigo (`electron-screen-share`) foi apagado e recriado como `murilobarbosa2002/zerohop`; o pacote npm também se chama `zerohop` agora (era `zero-hop`), o que muda a pasta de `userData` no Windows pra `%APPDATA%\zerohop\`.

Convenções de código, arquitetura, commits e Markdown estão modularizadas em `.claude/rules/` (carregam automaticamente, sem precisar ler manualmente) — cada arquivo cobre um tema (`code-style.md`, `react-components.md`, `commits.md`, etc.). **`.claude/rules/project-structure.md`** explica onde cada tipo de código mora e por quê, com exemplos reais; **`docs-site/tecnico/mapa-do-codigo.md`** é a versão exaustiva, arquivo por arquivo. Lições de bugs já resolvidos e por que não repeti-los ficam em `.claude/rules/bug-history-*.md`, escopadas por caminho de arquivo pra só entrar em contexto quando relevante.

## Decisões de arquitetura já tomadas

- **Sem servidor próprio.** Sinalização via PeerJS (broker público gratuito, `0.peerjs.com`). Vídeo/áudio sempre P2P direto (WebRTC).
- **TURN desativado de propósito.** O usuário decidiu explicitamente NÃO usar TURN (relay) — só STUN. Motivo: qualquer TURN gratuito viável tem limite de banda muito baixo (5GB/mês testado com Metered.ca) e o usuário prefere que a conexão falhe a depender de um relay limitado. Ver `src/renderer/src/services/room/turnCredentials.ts` — está fixo em STUN-only. **Não reativar TURN sem pedir confirmação explícita.**
- **Stack do renderer: React + TypeScript + Tailwind CSS, via `electron-vite`.** `npm run dev` = dev server com hot-reload; `npm run build` = bundle de produção em `out/`; `npm run typecheck` roda o `tsc -b --noEmit`. PeerJS é dependência normal do npm.
- **Visual retrô Windows 98/ICQ (v0.31.0+), pedido explícito do usuário.** Tokens de cor/raio remapeados em `tailwind.config.js` pra paleta cinza clássica (fundo `#d4d0c8`, texto preto, accent navy `#000080`); `src/renderer/src/index.css` tem duas regras globais que fazem o reskin cascatear automaticamente: `[class*='rounded-']:not(.rounded-full)` zera arredondamento (exceto `rounded-full`, reservado pra avatares/indicadores circulares) e `.border` aplica o bisel 3D em cima de qualquer elemento com essa classe Tailwind. Fonte é `Jersey10` (SIL OFL, local em `src/renderer/src/assets/fonts/`, `@font-face` local — **não carregar fontes de CDN externo em runtime**). Ao adicionar componente novo, usar sempre os tokens semânticos existentes (`bg-panel`, `border-border`, `text-text`, etc.) — é assim que o reskin continua se aplicando automaticamente.
- **Arquitetura de sala:** malha P2P (mesh) via `RoomClient`. Código de sala curto (6 caracteres) = ID do peer de quem criou a sala. Cada novo membro troca uma `DataConnection` com quem já está na sala (protocolo de "fofoca"/gossip pra propagar a lista de membros). Vídeo só é enviado a quem pede explicitamente ("watch-request"), não é broadcast automático.
- **Teclas de atalho globais — sem nenhuma dependência nativa desde a v0.36.22, com fallback híbrido desde a v0.36.25.** Mutar mic/áudio usam `globalShortcut` do Electron (sem dependência nativa). Push-to-talk é `keydown`/`keyup` do DOM no renderer (só funciona com o app em foco) **em paralelo** com `uiohook-napi` reativado como melhor esforço (funciona sem foco se a lib inicializar na máquina do usuário; se falhar, o fallback por DOM garante funcionamento com o app em foco). Ver `.claude/rules/bug-history-hotkeys.md` pro histórico completo de por que chegamos nessa decisão — **não tentar uma terceira dependência nativa de captura de teclado sem motivo muito forte.**
- **Push-to-talk reaproveita o mecanismo de mute normal** (`RoomClient.setMicMuted()`) em vez de um estado paralelo — mantém indicador visual e som de mute sempre corretos.
- **Mixer de efeitos sonoros por categoria (v0.36.9+).** 5 categorias (`SoundCategory`: Interface, Sala, Chat, Chamada de voz, Compartilhamento). Regras completas de como sons são estruturados/sintetizados em `.claude/rules/sound-effects.md` — ler antes de adicionar qualquer interação nova.
- **Múltiplas salas simultâneas (v0.35.0+).** `RoomClient` é uma classe autocontida sem estado global — várias instâncias vivas ao mesmo tempo. `useRoomSessions.ts` gerencia a lista de `RoomSession`; `App.tsx` só monta o `<Room>` completo (vídeo/chat/participantes) da sessão focada. **Voz é simultânea em todas as sessões abertas desde a v0.36.46** (decisão revertida — antes era exclusiva da sessão focada via `pauseVoice()`/`resumeVoice()`, removidos): microfone e chamadas de voz continuam ativos independente de foco, `App.tsx` monta um `RoomVoiceSink` por sessão *entrada* (não só a focada) pra tocar o áudio recebido. Vídeo (assistir tela de alguém) continua exclusivo da sessão em foco — só uma sala de vídeo renderizada por vez, de propósito, pra não precisar redesenhar o layout principal.
- **Contatos e sala pessoal (v0.36.20+).** Cada instalação gera um ID pessoal permanente (`services/personalRoomPreference.ts`, 10 caracteres) usado como `desiredCode` opcional em `RoomClient.createRoom()` — a "sala pessoal" é uma sala normal com código fixo. Contatos ficam em `contacts.json` (main process, `main/contacts.ts`), trocados manualmente fora do app. "Chamar" um contato passa pela mesma aprovação manual de entrada de qualquer sala. **Configurar a sala pessoal (ID/senha/auto-abrir) mora em Configurações → "Sala pessoal e convites" desde a v0.36.47** — a tela de Contatos só lista contatos salvos; abrir a sala pessoal continua na tela inicial (`PersonalIdPanel.tsx`).
- **Convidar contatos pra uma sala nova, pulando a aprovação (v0.36.25+).** Baseado em token de uso único (`RoomAuthController.preAuthorizeToken()`/`preAuthorizedTokens`), não em peer ID pré-autorizado — `joinRoom` sempre abre a conexão com um ID aleatório novo. O token viaja no `hello` (`helloMessageSchema.inviteToken`, opcional). **Verificação mútua por padrão** (só aceita convite de quem já é contato salvo), mas existe um toggle em Configurações (`allowUnknownInvites`, default `true`) pra aceitar convites de qualquer um — quem convida recebe aviso explícito se o destinatário recusou por ter essa opção desligada. Token expira em 5 minutos (`INVITE_TOKEN_TTL_MS`).
- **Instalador real via GitHub Actions, nunca via Wine.** Compilação do NSIS roda num runner Windows real do GitHub Actions (`.github/workflows/release.yml`, dispara em push de tag `v*`). **Nunca sugerir instalar Wine.**
- **Auto-update ativo** via `electron-updater` (`src/main/updater.js`), publicando em GitHub Releases. Só funciona em build empacotado (`app.isPackaged`).
- **`npm run dist:local` (WSL)** gera a pasta portátil só pra testes rápidos — não é o caminho de release oficial (ver `.claude/rules/build-and-release.md`).
- **Perfil obrigatório antes de entrar em sala (v0.36.48+).** Nome, avatar e status vivem na tela de Perfil (`components/ProfileScreen/`), não mais em Contatos. `hasProfileConfigured()` (nome não-vazio) bloqueia criar sala, entrar numa sala, chamar contato e abrir sala pessoal, mostrando um aviso com botão pra tela de Perfil em vez de deixar prosseguir. Status é broadcast pelo protocolo de sala junto com nome/avatar (fixo por sessão, mesma limitação de não atualizar ao vivo).
- **Highlight de sintaxe ao digitar no campo de mensagem (v0.36.55+).** `ChatInput.tsx` usa a técnica de "textarea invisível sobre um `<pre>` destacado": o texto real fica numa `<textarea>` com `text-transparent`/`caret-text` (só o cursor aparece), e um `<pre>` absolutamente posicionado atrás (`pointer-events-none`) mostra o texto de verdade, com blocos ` ``` ` destacados via `highlight.js` direto (`lib/highlightChatDraft.ts`). Os dois elementos precisam da mesma fonte/tamanho/padding/borda pra o cursor ficar alinhado com o texto visível — qualquer ajuste de estilo num precisa espelhar no outro. Cores dos tokens (`.draft-highlight` em `index.css`) são uma paleta própria pra fundo claro, diferente do tema `atom-one-dark` usado nas mensagens já enviadas (que tem fundo escuro).
- **Responder/reagir/editar mensagem no chat (v0.36.50+).** `ChatMessageEntry` ganhou `replyToId`, `edited` e `reactions`. Só o autor original pode editar a própria mensagem (`ChatService.receiveEdit` valida `message.fromId === fromId`); reagir de novo com o mesmo emoji remove a própria reação (toggle).
- **Busca e favoritos em Contatos (v0.36.51+).** `Contact` ganhou `favorite?: boolean`, persistido em `contacts.json` como qualquer outro campo (sem canal IPC novo, `updateContact` já aceita o objeto inteiro). Favoritos sempre no topo da lista; busca filtra pelo apelido, client-side.
- **Painéis redimensionáveis da sala respeitam a largura real da janela (v0.36.54+).** `sidebarWidth`/`chatWidth` (`useResizablePanelWidth`) guardam a largura *desejada* do usuário (persistida), mas `Room.tsx` calcula uma largura *renderizada* a partir de `useWindowWidth()`, sempre deixando `ROOM_STAGE_MIN_WIDTH_PX` (`constants/layout.ts`) de espaço pra área de vídeo — evita que os painéis lateral/chat sejam cortados pela borda da janela quando a soma das larguras não cabe (janela restaurada/pequena).
- **Nome de contato sobrepõe o nome transmitido, só localmente (v0.36.52+).** `lib/resolveContactDisplayName.ts` troca o nome exibido de um membro pelo apelido salvo em Contatos quando `member.personalId` bate com um `contact.id` — usado em `ParticipantTile` e nas mensagens de chat (`Room.tsx` resolve `fromName` antes de passar pro `<Chat>`). Não é sincronizado nem broadcastado — cada lado vê o apelido que *ele próprio* salvou, igual ao resto do sistema de contatos.

## Ambiente de build

- Build acontece em WSL/Linux (sem Wine — decisão deliberada).
- Testes automatizados em `e2e/` (`npm run test:e2e`), `playwright-core` + `xvfb-run` contra o binário do Electron, com `ELECTRON_RUN_AS_NODE=` vazio (o WSL do usuário seta essa variável globalmente).
- CI (`.github/workflows/ci.yml`) roda typecheck, build, lint:md e `e2e/` a cada push na `main` e a cada PR.

## Ferramentas externas usadas

- **PeerJS** — dependência normal do npm (`peerjs`), usada em `services/room/*` — sinalização.
- **`react-markdown` + `remark-gfm` + `rehype-highlight`/`highlight.js`** — renderização de Markdown no chat (v0.36.49+). Deliberadamente `react-markdown` (renderiza pra React, não HTML bruto) em vez de `marked`/`dangerouslySetInnerHTML` — mensagens vêm de peers não confiáveis da sala.
- Ícone gerado via `sharp` + `to-ico` (instalados com `--no-save`, não são dependência permanente do projeto).
